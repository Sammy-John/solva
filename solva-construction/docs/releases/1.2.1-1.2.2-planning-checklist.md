# Release 1.2.1 and 1.2.2 Planning Checklist

This checklist splits the next work into two safer releases:

- **1.2.1** focuses on fixing export reliability and adding a readable Excel export.
- **1.2.2** focuses on the People model upgrade, migration safety, snapshots, and People UI polish.

No implementation should start until the relevant release checklist is reviewed and approved.

## Release 1.2.1: Export Fixes and Excel Export

### Goal

Make schedule export reliable and client-readable. CSV export should be checked and fixed, while Excel export becomes the preferred shareable format.

### Scope

- [ ] Investigate why current CSV export is not working.
- [ ] Fix CSV export or clearly retain it as a fallback if Excel becomes primary.
- [ ] Add Excel export as `.xlsx`.
- [ ] Format the Excel workbook for a receiver who may not use the app.
- [ ] Include project and export context in the workbook.
- [ ] Verify export works in browser/dev mode and installed Tauri app mode if applicable.

### Proposed Excel Workbook

- [ ] Sheet: `Schedule`
  - [ ] Project name
  - [ ] Export date
  - [ ] Section
  - [ ] Task
  - [ ] Type
  - [ ] Status
  - [ ] Start date
  - [ ] End date
  - [ ] Duration
  - [ ] Assigned person or company
  - [ ] Waiting On / dependency detail
  - [ ] Comments / notes
- [ ] Sheet: `People`
  - [ ] People currently used by the project or schedule
  - [ ] Role/type where available
  - [ ] Company where available
  - [ ] Contact details where available
- [ ] Optional sheet: `Attention`
  - [ ] Delayed tasks
  - [ ] Blocked tasks
  - [ ] Inspection milestones
  - [ ] Tasks with dependency warnings

### Formatting Requirements

- [ ] Freeze header rows.
- [ ] Bold table headers.
- [ ] Use readable column widths.
- [ ] Apply date formatting.
- [ ] Preserve dependency and Waiting On text in a readable form.
- [ ] Avoid raw IDs where names or labels are available.
- [ ] Ensure empty values are represented cleanly.

### Tests and Verification

- [ ] Add or update tests for export data shaping.
- [ ] Manually export a real construction starter schedule.
- [ ] Open the generated Excel file and confirm formatting is readable.
- [ ] Confirm CSV export still works or document replacement behavior.
- [ ] Run `npm run test`.
- [ ] Run `npm run build`.

### Release Decision

- [ ] Confirm no People model changes are included in 1.2.1.
- [ ] Confirm export changes are merged and released before starting 1.2.2.

## Release 1.2.2: People Directory and Project People Upgrade

### Goal

Turn People into a proper master directory and project team system while protecting existing client data and preserving historical task assignments.

### Core Model

- [ ] Add a master People directory for all internal people, suppliers, subcontractors, inspectors, consultants, and client contacts.
- [ ] Add per-project People membership.
- [ ] Allow people to be active or inactive for a project.
- [ ] Keep inactive people visible on historical/completed task assignments.
- [ ] Hide inactive project people from new task assignment dropdowns.
- [ ] Prefer archive/inactive behavior over destructive deletion.

### People Data Fields

- [ ] Name
- [ ] Type: Internal, Supplier, Subcontractor, Inspector, Client, Consultant, Other
- [ ] Company
- [ ] Role/trade
- [ ] Email
- [ ] Phone
- [ ] Notes
- [ ] Active/archived state

### Entry Page and Navigation

- [ ] Add a top-level People section on the main entry page.
- [ ] Make the People section the management surface for the master directory.
- [ ] Show enough information to distinguish people with similar names.
- [ ] Support adding, editing, archiving, and reviewing usage.

### New Project Flow

- [ ] Add a step or panel to select active people for the new project.
- [ ] Use checkboxes from the master People directory.
- [ ] Allow adding a new person during project setup.
- [ ] Ensure newly added people are added to the master directory and selected for the project.

### Existing Project Flow

- [ ] Add project People management to the project workspace/settings.
- [ ] Allow adding people from the master directory to the project.
- [ ] Allow adding new people to both the master directory and current project.
- [ ] Allow deselecting people from future use on the project.
- [ ] Warn when deselecting a person who is assigned to active tasks.
- [ ] Keep deselected people on completed/historical tasks.

### Task Assignment Behavior

- [ ] Assignment dropdowns should use active project people by default.
- [ ] Existing assigned people should continue to render even if inactive.
- [ ] If an inactive person is assigned to an active task, provide a clear warning or review path.
- [ ] Waiting On/dependency details should continue to resolve names after people are archived or deselected.

### Migration and Safety

- [ ] Detect legacy project-level people that have not been upgraded to the master directory model.
- [ ] Add a health/status warning when a people upgrade is available.
- [ ] Add a `Review People Upgrade` action.
- [ ] Use an approval modal before changing legacy people data.
- [ ] Recommend saving a snapshot before approving the upgrade.
- [ ] Show a preview of people that will be created, matched, or selected for the current project.
- [ ] Make the migration idempotent so running it twice does not duplicate people.
- [ ] Use conservative matching rules to avoid accidental merges.
- [ ] Provide `Not Now` so the user can defer the upgrade.

### Backup and Restore

- [ ] Confirm the client has a copy of the database before upgrading app version or running migration.
- [ ] Add or document a pre-upgrade database backup path.
- [ ] Ensure snapshots include the project people state required to restore the worksheet.
- [ ] Ensure snapshots preserve task assignment display names even when people are later inactive or archived.
- [ ] Ensure restore can recover from a failed or unwanted legacy people upgrade.
- [ ] Clearly distinguish project snapshot restore from full workspace/database restore.

### Save, Load, and Snapshot Behavior

- [ ] Save master People directory changes correctly.
- [ ] Save project People membership correctly.
- [ ] Load active and inactive project People correctly.
- [ ] Restore task assignments without missing names.
- [ ] Restore Waiting On/dependency people references without broken labels.
- [ ] Verify restore does not accidentally erase unrelated people from other projects unless performing a full database restore.

### People UI Styling

- [ ] Update styling for all People-related UI.
- [ ] Align People screens with the current design system.
- [ ] Improve empty states.
- [ ] Improve destructive/archive confirmation copy.
- [ ] Ensure mobile layouts remain usable.
- [ ] Ensure dropdowns, modals, and project setup controls are consistent.

### Tests and Verification

- [ ] Add tests for master directory creation/editing.
- [ ] Add tests for project People membership.
- [ ] Add tests for task assignment dropdown filtering.
- [ ] Add tests for inactive people remaining visible on existing tasks.
- [ ] Add tests for migration/idempotency.
- [ ] Add tests for save/load/restore with People data.
- [ ] Manually test upgrade from an existing schedule.
- [ ] Manually test snapshot restore after migration.
- [ ] Run `npm run test`.
- [ ] Run `npm run build`.

### Release Decision

- [ ] Confirm 1.2.1 export work is released before beginning 1.2.2.
- [ ] Confirm migration copy and UI text with client before release.
- [ ] Confirm snapshot restore path before shipping.
- [ ] Confirm release notes explain the People upgrade clearly.
